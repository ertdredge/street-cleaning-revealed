# Logging to Grafana Cloud Loki

`logMsg(level, fmt, ...)` (in `loki-log.h/.cpp`) replaces every `Serial.printf` / `Serial.println` log call in the sketch.
It prints to Serial immediately, then queues the line for Loki.

- **Never blocks the serial side.** `logMsg` only formats, prints and copies the line into a 12 KB byte ring (variable-length records, roughly 100 typical lines; the first version held 24 fixed-size lines and overflowed on the hourly burst, which is a poll plus its report, about 45 lines). The HTTPS POST is made by `lokiFlush()`, called from the weather task (core 0) every 5 s, up to three batches per round; a batch holds up to 40 lines or about 12 KB of JSON. A slow or failed POST (8 s timeouts) delays only that task. If the ring does overflow, the oldest queued lines are dropped from the Loki queue (not from Serial) and a warning line records how many; the heartbeat carries running totals.
- **Function name.** `logMsg` is a macro that passes `__func__`, which is sent as Loki structured metadata (`["ts","line",{"func":"pollSnowEmergency"}]`); query with `{app="street-cleaning-reveaLED"} | func="pollSnowEmergency"`. This needs Loki 3.x with structured metadata enabled. If the stack refuses it (HTTP 400; the Loki error text is shown on Serial as `loki: refused: ...`), build with `-DLOKI_FUNC_MODE=1` to put `func=NAME ` at the start of each Loki line instead. Serial output never includes the function name.
- **Report after each feed poll.** After every round of feed polling (the forecast fetch and/or the city feed poll, whether it succeeded or was abandoned to retry), including the first one after boot, the sketch logs the same output as the `time`, `forecast` and `status` commands, at info level, under a `report: state after a feed poll` line. It runs in `loop()` on core 1 so it can read the display state. If a manual command (`left`, `right`, `off`, ...) has put the display in manual mode, the `time` part is replaced by a one-line note, because `time` would take the display back to clock mode. The forecast and city polls are scheduled separately, so they can drift apart and give two reports an hour. The `forecast` part includes each night's forecast low against the typical low (`last night`, `tonight`, `tomorrow night`...), and the `top:` lines of the `time` part give the bar length and the notch pixels.
- **Levels** (stream label `level`): `debug` for the verbose render dump from the `time` command (`now`, `top:`, `snow:`, `waste:`, bar speeds; the same lines are info level inside the post-poll report); `info` for command acknowledgements, status and forecast reports, fetch successes; `warn` for fetch failures, usage errors and bad input. `error` exists but nothing uses it yet. Stream labels: `app` is `street-cleaning-reveaLED`, `kind` is `log` or `heartbeat`, `level` as above.
- **Timestamps.** Loki's push API requires a timestamp on every line, so none can be omitted. Lines logged before NTP succeeds wait in the queue; once the clock is valid they are sent with a timestamp computed as (current real time − how long ago they were logged, from `millis()`). If NTP never succeeds, nothing is sent. The timestamp uses `realNow()`, so the simulated clock (`time`, sweeps, `test-suite`) does not skew it. Lines longer than 319 characters are cut in Loki (Serial gets up to 383).
- **Failures.** Backoff 15 s, 30 s, 60 s, 120 s, then 300 s between attempts, keeping the batch until it succeeds, except HTTP 400/413/422 (the batch itself is refused), which drops the batch. The sender's own messages (`loki: ...`) are Serial only, so they cannot feed back into the queue.
- **Security.** The connection uses `setInsecure()` (no certificate check), as the NWS fetch does, so the token could be captured by a man in the middle on your network. Use a token scoped to `logs:write`. To fix, pin the Grafana Cloud root CA with `setCACert` (TODO in `loki-log.cpp`).
- **secrets.h** needs `LOKI_URL` (base, e.g. `https://logs-prod-XXX.grafana.net`, a trailing slash is tolerated), `LOKI_USER`, `LOKI_TOKEN`.

Query in Grafana Explore: `{app="street-cleaning-reveaLED"}`, or `{app="street-cleaning-reveaLED", level="warn"}`.

## Heartbeat

Every 10 minutes (the first one at boot, even before WiFi or NTP, so it is queued and back-dated), `sendHeartbeat()` logs one logfmt line into its own stream, `kind="heartbeat"` (level info). It is also printed on Serial.

    event=heartbeat uptime_s=… heap_free=… heap_min=… heap_block=… wifi_up=1 rssi=-61 wifi_reconnects=0 forecast_age_min=12 emergency_age_min=12 est_ma=180 temp_c=47.2 reset_reason=power_on loki_pending=3 loki_dropped=0 loki_post_failures=0

- `heap_min` is the low-water mark since boot and `heap_block` the largest allocatable block (fragmentation). `wifi_reconnects` counts connections after the first. `*_age_min` is -1 until a good fetch.
- `est_ma` is FastLED's `calculate_unscaled_power_mW()` of the frame being shown, at 5 V: an estimate of pixel current, not a measurement.
- `temp_c` is the ESP32 die temperature (`temperatureRead()`), uncalibrated and good only for trends. It is left out if the core returns NaN. A constant 53.3 means the sensor is not working (a known quirk of classic-ESP32 builds with some core versions).
- `reset_reason` is why the chip last restarted: `brownout`, `panic`, `task_wdt`, `int_wdt`, `power_on`, ... Repeated `brownout` means the 5 V rail is sagging.

Grafana: chart `{app="street-cleaning-reveaLED", kind="heartbeat"} | logfmt | unwrap heap_free`. Suggested alerts: `absent_over_time({app="street-cleaning-reveaLED", kind="heartbeat"}[30m])` (board, WiFi or token is down); `forecast_age_min > 600` (the top strip is about to go dark); `loki_dropped` increasing; `reset_reason="brownout"`.
